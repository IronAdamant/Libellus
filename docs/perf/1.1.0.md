# Libellus performance 1.1.0

Same machine and the same `examples/perf.rs` harness as
[baseline-1.0.0.md](baseline-1.0.0.md). Figures are median microseconds,
then p95. The 10000-note list and brief rows are 5 runs, so the p95 is coarse.

## What changed

- Listing and the brief read note files on several threads once an agent has
  128 or more notes. Fewer than that stays single-threaded.
- `libellus_spend` keeps the ledger entries it already checked for damage and
  does not read the file a second time to compute totals.

## Before and after

| Path | 1.0.0 median / p95 | 1.1.0 median / p95 |
|---|---:|---:|
| ls, 10 notes | 47 / 95 | 40 / 65 |
| ls, 1000 notes | 3329 / 5600 | 2684 / 3726 |
| ls, 10000 notes | 43373 / 58492 | 29522 / 35301 |
| brief, 10000 notes | 40044 / 41006 | 29503 / 30579 |
| brief, 10000 notes and ledger | 54169 / 56381 | 38492 / 42985 |
| spend, growing through entries 10 to 999 | 1780 / 3076 | 1080 / 2217 |
| spend, 10000 entries already stored | 20240 / 21385 | 14065 / 14441 |
| CLI cold brief, 10000 notes | 61836 / 65492 | 39586 / 42092 |
| MCP cold brief | 65499 / 71404 | 38408 / 39346 |
| MCP warm brief | 51567 / 66815 | 36546 / 40526 |

List, brief, spend, and the brief-shaped CLI and MCP calls are faster because
they do less repeated reading. On this 4 CPU machine a 10000-note list fell
from about 43 ms to about 30 ms, and a spend against a 10000-line ledger fell
from about 20 ms to about 14 ms.

The list and brief gain comes from reading note files on several threads. On
1 CPU that fan-out has nothing to run beside the caller, so the gain
disappears and the extra thread setup can make a list slightly slower. Get of
one note never takes that path.

## What did not improve

- Reading one note stays about 6 microseconds. It was already one file.
- Writing a note stays about 160 to 180 microseconds. Each write still syncs
  its own file. This run was slightly slower than the baseline. That is noise,
  not a win.
- A full ledger read of 10000 lines was 9434 / 9538 us before and 11874 / 14970
  us after, about 19 to 26 percent slower at the median. `ledger::read` was
  not changed between those runs. The harness repeats that read only 10 times,
  and the p95 moved even more, so this is run-to-run noise on a small sample,
  not a slower parser. It is not a fix and it is not a regression in the code.
- `libellus --version` stays under about 1 ms. Process start was not the cost
  of a brief.
- `read_strict` on a 4 MiB fixture stays under about 1 ms at the median. The
  p95 bounced between runs (1880 before, 3113 after). Large reads were not a
  hotspot next to opening thousands of notes.
- Store file sizes are unchanged. 10000 notes are 1437780 bytes and the
  10000-line ledger in this harness is 1222440 bytes.
