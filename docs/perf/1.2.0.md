# Libellus performance 1.2.0

Release build, measured on this machine before and after the 1.2.0 changes.
The 1.1.2 column is the same binary that was current at the start of the
work (`target/release/libellus` reporting 1.1.2), not the numbers from the
stress-test box. That box had 8 CPUs. This one has 4. Do not compare these
milliseconds with the stress-test report's milliseconds.

`spend` now keeps `ledger.meta`. A later spend skips parsing when the file
length and the last line still match. The first spend after a hand-written
ledger is the cold sample. Per-task totals are cached for up to 64 tasks.
With more tasks, spend still reads the ledger to total that one task.

The brief and `ledger` still read the ledger file. Grouping is one pass, so
the old quadratic cost in the number of distinct tasks is gone. The brief
also caps its text, which is why 100 open questions went from 19001 bytes
to 927 bytes at `--max_items 3`.

## Machine

- Linux 6.12.113+ #1 SMP PREEMPT_DYNAMIC Mon Nov 23 16:05:51 UTC 2026 x86_64
- rustc 1.83.0 (90b35a623 2024-11-26)
- model name : Intel(R) Xeon(R) Processor
- CPUs: 4
- MemTotal: 15 GiB
- host triple: x86_64-unknown-linux-gnu

Times are wall-clock milliseconds of one `libellus` process. The spend rows
for 1.2.0 list the cold sample and then the warm samples. Median of the warm
samples is the last figure in that cell.

## Spend, one task

The ledger was seeded with identical lines, then `spend` was timed.

| Stored entries | 1.1.2 median | 1.2.0 cold | 1.2.0 warm samples | 1.2.0 warm upper-middle |
|---:|---:|---:|---|---:|
| 1,000 | 4.3 ms | 3.3 ms | 1.3, 2.4, 1.3, 1.0 ms | 1.3 ms |
| 10,000 | 24.5 ms | 23.0 ms | 4.5, 2.3, 3.7, 1.9 ms | 3.7 ms |
| 100,000 | 274.1 ms | 183.3 ms | 3.9, 1.6 ms | 3.9 ms |

The cold spend still reads the file. The warm spend does not. A ledger with
100,000 entries and 40 tasks (under the 64-task cache) was 146.7 ms per spend
on 1.1.2. After `brief` had filled the cache, the next two spends were 12.7 ms
and 4.0 ms, and the task total was 2502 entries, which matches the file.

## Brief and ledger, one row per task

Each ledger line is a distinct task. `brief` bytes are the text (1.2.0) or
the whole stdout (1.1.2, which was also text).

| Tasks | 1.1.2 brief | 1.2.0 brief | 1.1.2 ledger | 1.2.0 ledger | 1.1.2 spend | 1.2.0 spend |
|---:|---:|---:|---:|---:|---:|---:|
| 40 | 1.0 ms | 2.9 and 2.8 ms | 1.1 ms | 2.9 and 2.4 ms | 1.9 ms | 2.8 ms |
| 2,000 | 12.1 ms | 6.3 and 6.9 ms | 8.9 ms | 7.8 and 7.6 ms | 7.5 ms | 7.1 ms |
| 20,000 | 319.9 ms | 45.4 ms | 294.5 ms | 59.9 ms | 40.1 ms | 35.1 ms |
| 100,000 | 13.1 s | 227 ms | 13.5 s | 336 ms | 246 ms | 141 ms |

At 40 tasks the 1.2.0 brief is a few milliseconds slower. It writes the
current-state section and the totals cache. The 100,000-task brief is about
58 times faster than 1.1.2 on this machine, and the reply is 597 bytes
instead of a multi-megabyte `by_task` map. `libellus ledger` still returns
every task: 7,089,100 bytes at 100,000 tasks. That is the full breakdown,
and it is the slow part of that command (336 ms, down from 13.5 s).

The 100,000-task spend (141 ms) still reads the ledger, because 100,000 task
rows are not cached. Caching them made one spend take 26.9 s on this machine,
which is worse than 1.1.2, so the cache stops at 64 tasks.

## Brief size

100 open questions, summaries of 180 characters, `--max_items 3`:

| | bytes | time |
|---|---:|---:|
| 1.1.2 | 19001 | 1.8 ms |
| 1.2.0 | 927 | 1.2 ms |

1.1.2 listed every question. 1.2.0 lists the newest 3 and says the rest were
omitted. The text cap is 8192 bytes.

## What this does not claim

- Warm spend times are for a ledger whose length and last line still match
  `ledger.meta`. A same-length edit of an earlier line is invisible to spend
  until `brief`, `ledger` or `check` rewrites the cache.
- A cold spend, and any spend once there are more than 64 tasks, still grows
  with the ledger.
- These are one machine, one release build, a handful of samples. They are
  not a general throughput claim.
